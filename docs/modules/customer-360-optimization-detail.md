# 客户 360 页面优化探索文档

## 1. 背景与目标

- 路由：`/customers/360`
- 当前实现：`src/views/customers/360/index.vue`
- 关联需求：`docs/modules/route-feature-requirements.md`
- 本次目标：先不修改代码，只明确客户 360 页面下一步优化方向，要求简洁、能闭环、后续可小步落地。

客户 360 页面不应该只是客户资料展示页。它更适合承担一个清晰业务任务：

```text
选中客户 -> 看清客户状态 -> 找到风险和关键触点 -> 执行下一步动作 -> 记录处理结果 -> 回到客户状态验证
```

推荐定位：

```text
客户档案驾驶舱 + 互动时间线 + 下一步行动闭环
```

## 2. 项目结构与现状分析

### 2.1 已分析文件

| 文件 | 作用 | 结论 |
| --- | --- | --- |
| `src/views/customers/360/index.vue` | 客户 360 页面实现 | 当前是三栏雏形，但不建议继续强化三栏；三栏会分散客户状态、证据和动作闭环 |
| `src/views/customers/journey/index.vue` | 相邻客户旅程页面 | 同样使用轻量工作台结构，可保持客户中心风格统一 |
| `src/api/business.ts` | 通用业务记录接口类型 | 当前可复用字段有限，适合先做轻量闭环，不宜新增复杂数据模型 |
| `src/mock/business.ts` | 通用 mock 数据 | `customers-360` 已有 3 条记录，可支撑列表、选择、状态变更、时间线 |
| `docs/modules/route-feature-requirements.md` | 路由功能要求 | 客户 360 应覆盖档案、工单、会话、电话、邮件、订单合同、风险标签、客户价值和 next-best action |
| `docs/design-system/visual-language.md` | 视觉原则 | 页面应保持企业运营台风格，信息密度高但可读 |
| `docs/design-system/component-system.md` | 组件方向 | 可用 Customer Card、Timeline、Command Panel、Drawer 等现有设计语言 |

### 2.2 当前页面结构

```text
顶部说明 + 搜索/状态筛选 + 查询/刷新/打开档案
└── 三栏工作区
    ├── 左侧：客户档案
    ├── 中间：互动时间线
    └── 右侧：下一步建议
```

说明：这是当前页面结构，不是推荐结构。客户 360 的关键不是同时铺开三个面板，而是让用户沿着“客户状态 -> 风险证据 -> 下一步动作 -> 处理结果”顺序完成判断和处置。

### 2.3 当前主要问题

| 问题 | 现象 | 影响 |
| --- | --- | --- |
| 客户选择不清楚 | 页面默认只取第一条记录，且选择关系弱 | 用户不知道当前看的是哪个客户，也无法探索其他客户 |
| 档案信息太少 | 只显示客户名、价值等级、续约临近和标签 | 不像 360，缺少客户状态判断依据 |
| 时间线只是记录列表 | 当前展示 `records`，但没有按客户或事件类型组织 | 用户难以从时间线定位风险原因 |
| 下一步动作不可闭环 | `安排回访` 只把状态改成 `处理中` | 没有负责人、动作目标、验证结果和关闭条件 |
| 抽屉入口不完整 | 有详情抽屉代码，但主页面没有明显打开详情的入口 | 已有能力没有被页面使用起来 |
| 页面价值不聚焦 | 页面描述覆盖资料、工单、会话、电话、邮件、订单合同等很多内容 | 一次做全会变复杂，容易走向大改 |

## 3. 优化方向对比

### 方向 A：继续三栏增强

核心思路：沿用当前三栏，把客户档案、互动时间线、下一步建议分别做得更完整。

优点：

- 改动最小。
- 基本复用现有 `BusinessRecord` 字段。

不足：

- 信息被横向切散，用户视线需要在三块之间来回跳。
- 左右侧容易变成静态说明，中间变成列表，闭环路径不明显。
- 宽屏下看似丰富，实际没有突出“当前客户应该怎么处理”。

适合场景：

- 只做非常短期的占位页美化。

推荐程度：不推荐作为本次方向。

### 方向 B：互动时间线工作台

核心思路：用纵向主线组织页面，把客户概览、关键证据、互动时间线和处理动作按业务顺序排列。

优点：

- 更符合客户 360 的核心定义。
- 可以形成“从触点发现风险”的体验。
- 不依赖三栏，用户按从上到下的处理路径阅读。

不足：

- 当前数据模型没有真实触点类型、合同、订单、渠道明细。
- 如果强行补齐所有触点，会出现大量假字段，后续容易返工。

适合场景：

- 适合做为首轮结构方向，但触点内容需要克制，先复用现有时间线。

### 方向 C：下一步行动闭环

核心思路：围绕高价值客户续约风险、画像补全、互动回访三类记录，形成“客户状态 -> 风险证据 -> 推荐动作 -> 状态推进 -> 时间线验证”的小闭环。

优点：

- 简洁，业务目标明确。
- 可复用现有 `BusinessRecord`、`status`、`aiSuggestion`、`timeline`。
- 不需要新增接口也可以先落地。
- 后续扩展真实客户资料和触点接口时，页面结构不用推翻。

不足：

- 不是一次性做完整客户 360。
- 客户价值、续约日期、合同金额等只能先用展示型派生数据或 mock 展示。

推荐程度：优先推荐。

## 4. 推荐方案

推荐采用方向 B + 方向 C：不用三栏，改成纵向闭环工作流。

```text
客户检索/切换 -> 客户状态总览 -> 风险与证据 -> 互动时间线 -> 下一步行动 -> 详情抽屉验证
```

页面只解决一个核心业务问题：

```text
今天应该优先跟进哪个客户，以及跟进后如何确认这件事已经闭环。
```

## 5. 为什么不采用三栏布局

三栏看起来符合“360 信息很多”的直觉，但不适合这个页面的首轮优化。

原因：

- 客户 360 的业务动作是顺序型，不是并列型。用户要先确认客户，再看风险证据，再决定下一步动作。
- 三栏会把“档案、历史、建议”拆开，页面像资料陈列，而不是处理工作流。
- 当前数据模型很轻，三栏会暴露字段不足的问题，容易靠假数据撑版面。
- 右侧建议如果长期固定，会变成孤立建议卡，无法自然承接时间线和状态推进。
- 窄屏下三栏最终还是会折成单列，不如一开始就设计成清晰的纵向流程。

所以推荐的不是“三栏客户档案页”，而是：

```text
纵向客户处理台
```

## 6. 推荐首屏布局

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 客户 360  搜索客户/记录/负责人  状态筛选        查询  刷新  新建跟进       │
├────────────────────────────────────────────────────────────────────────────┤
│ 客户切换条：蓝湖集团 高风险 待处理 | 星河科技 中风险 处理中 | 云杉零售 已完成 │
├────────────────────────────────────────────────────────────────────────────┤
│ 客户状态总览                                                                │
│ 蓝湖集团  高价值客户续约风险  高风险  负责人 陈沐阳  状态 待处理  最近更新   │
│ 标签：客户 / 待处理 / 高       AI 建议：建议先回访续约临近且情绪下降的客户     │
├────────────────────────────────────────────────────────────────────────────┤
│ 风险与证据                                                                  │
│ 风险：续约临近 + 情绪下降                                                    │
│ 证据：最近互动历史需回访 / 客户画像待补全 / 高价值标签                         │
│ 推荐动作：安排回访，并补全客户画像                                            │
├────────────────────────────────────────────────────────────────────────────┤
│ 互动与闭环时间线                                                            │
│ AI 分析：建议先回访续约临近且情绪下降的客户                                  │
│ 业务接入：客户记录已进入工作台                                                │
│ 状态变更：状态已调整为处理中                                                  │
├────────────────────────────────────────────────────────────────────────────┤
│ 下一步行动：安排回访  提交审核  标记完成                         查看详情     │
└────────────────────────────────────────────────────────────────────────────┘
```

布局建议：

- 顶部保留搜索、筛选和新建跟进。
- 搜索下方使用横向客户切换条，不做固定左栏。
- 客户状态总览放在首屏主位置，先回答“当前客户是谁、处于什么风险、谁负责”。
- 风险与证据紧跟客户状态，避免建议脱离依据。
- 时间线作为主内容区域，展示处理过程和变化。
- 下一步行动放在时间线后或页面底部粘性操作区，承接闭环，不做孤立右侧栏。
- 抽屉用于查看更多详情和完整闭环记录，不要把所有字段堆在首屏。

## 7. 闭环设计

### 7.1 最小状态流

直接复用现有状态，不新增状态枚举：

```text
待处理 -> 处理中 -> 待审核 -> 已完成
```

状态含义：

| 状态 | 客户 360 语义 | 页面动作 |
| --- | --- | --- |
| 待处理 | 发现客户风险或资料缺口 | 安排回访、补全画像 |
| 处理中 | 已有人负责跟进 | 查看跟进动作、继续处理 |
| 待审核 | 等待主管或客户成功经理确认 | 验证处理结果 |
| 已完成 | 风险已处理或资料已补全 | 归档到历史 |

暂不建议在本轮引入“待回访、待验证、已闭环”等新枚举，避免影响其他共用 `BusinessRecordStatus` 的页面。

### 7.2 页面闭环路径

```text
1. 用户通过顶部搜索或客户切换条选择一条记录。
2. 页面展示客户状态总览、风险证据、AI 建议和历史时间线。
3. 用户在底部行动区点击主动作，例如“安排回访”。
4. 记录状态从“待处理”变为“处理中”，时间线追加状态变更。
5. 用户打开详情抽屉查看完整闭环记录。
6. 后续再推进到“待审核”或“已完成”。
```

### 7.3 最小可落地动作

| 动作 | 当前接口是否支持 | 建议 |
| --- | --- | --- |
| 切换客户记录 | 支持，使用 `records` 和 `active` | 优先做 |
| 查看详情抽屉 | 已有 `detailOpen` 和 `detailRecord` | 优先做 |
| 安排回访 | 支持，调用 `updateBusinessRecordStatus` | 保留，但文案更业务化 |
| 标记待审核 | 支持，调用 `updateBusinessRecordStatus` | 可作为第二动作 |
| 标记已完成 | 支持，调用 `updateBusinessRecordStatus` | 可作为详情抽屉动作 |
| 新建跟进记录 | 已支持 `createBusinessRecord` | 保留，不扩展复杂表单 |

## 8. 首轮最小改造范围建议

如果后续进入代码实现，建议只改一个文件：

```text
src/views/customers/360/index.vue
```

建议改动：

| 优先级 | 改动 | 说明 |
| --- | --- | --- |
| P0 | 顶部增加客户切换条 | 解决“当前客户不清楚”，且避免固定三栏 |
| P0 | 主区域展示客户状态总览 | 解决“360 信息不聚焦” |
| P0 | 增加风险与证据区 | 让 AI 建议有依据 |
| P0 | 时间线只展示当前记录 | 解决记录列表和客户状态脱节 |
| P0 | 底部行动区显示状态、负责人、AI 建议和主动作 | 解决“下一步不知道做什么” |
| P0 | 记录项或按钮打开详情抽屉 | 复用已有抽屉能力 |
| P1 | 增加状态推进按钮：安排回访、提交审核、完成 | 形成更完整闭环 |
| P1 | 加入空状态和加载态 | 防止数据为空时页面破碎 |
| P2 | 视觉细节整理 | 只做局部样式，不抽公共组件 |

不建议首轮做：

- 新增客户 360 专属 API。
- 新增复杂客户画像类型。
- 把共用业务记录模型改成客户域模型。
- 抽公共组件或重构多个页面。
- 引入图表库或关系图。
- 继续强化三栏布局。

## 9. 具体内容建议

### 9.1 顶部：客户切换条

用途：回答“今天要看哪些客户”。

显示字段：

- 记录标题。
- 客户名称。
- 风险等级。
- 状态。
- 负责人。
- 最近更新时间。

交互：

- 点击记录切换 `active`。
- 当前选中记录高亮。
- 双击或点击“详情”打开抽屉。

### 9.2 主区域一：客户状态总览

用途：回答“这个客户现在是什么情况，为什么需要处理”。

客户摘要字段：

- 客户名称。
- 当前记录标题。
- 负责人。
- 状态。
- 优先级。
- 风险等级。
- 标签。
- 说明。

建议表现：

- 摘要不要做成很多卡片，使用一块紧凑信息区。
- 如果没有选中记录，显示“请选择客户记录”。

### 9.3 主区域二：风险与证据

用途：回答“为什么要处理这个客户”。

显示字段：

- 风险等级。
- 当前风险描述。
- 关联标签。
- AI 建议。
- 可验证依据。

建议表现：

- 不引入复杂图表。
- 可以用 2 到 3 行证据列表表达。
- 证据必须来自现有字段：`risk`、`description`、`tags`、`aiSuggestion`、`timeline`。

### 9.4 主区域三：互动与闭环时间线

用途：回答“这个客户已经发生过什么，处理进展到哪一步”。

时间线字段：

- 动作名称。
- 动作内容。
- 操作人。
- 时间。

建议表现：

- 只展示当前选中记录的 `active.timeline`。
- 时间线是主内容，不放在窄栏。
- 状态变更后刷新时间线，让用户看到动作已记录。

### 9.5 底部：下一步行动

用途：回答“下一步做什么，做完如何推进”。

显示字段：

- AI 建议。
- 当前状态。
- 负责人。
- 推荐动作。
- 验证口径。

推荐动作映射：

| 当前状态 | 主按钮 | 次按钮 |
| --- | --- | --- |
| 待处理 | 安排回访 | 打开详情 |
| 处理中 | 提交审核 | 打开详情 |
| 待审核 | 标记完成 | 打开详情 |
| 已完成 | 查看闭环 | 无 |
| 已暂停 | 恢复处理 | 打开详情 |
| 已关闭 | 查看闭环 | 无 |

建议表现：

- 行动区不要作为右侧栏，而是放在时间线后或底部粘性区域。
- 主按钮只保留一个，减少判断成本。
- 次按钮只保留“查看详情”或“提交审核”等与当前状态强相关的动作。

## 10. 需要和用户确认的疑点

这些点如果要进入代码实现，建议先确认后再调整：

| 疑点 | 为什么需要确认 | 默认建议 |
| --- | --- | --- |
| 客户 360 是否以“客户”为主，还是以“跟进记录”为主 | 当前数据是 `BusinessRecord`，不是 Customer 实体 | 首轮以跟进记录驱动，避免新增模型 |
| 是否允许把“打开档案”改成“新建跟进” | 当前按钮文案和弹窗行为不一致 | 建议改为“新建跟进” |
| “安排回访”后是否直接进入处理中 | 当前接口只能改状态，没有回访任务实体 | 可以先进入处理中 |
| 是否需要展示订单/合同金额 | 当前没有字段 | 首轮不做，避免假数据过多 |
| 是否需要真实客户列表接口 | 当前 mock 只有通用记录 | 首轮不新增接口，后续再单独设计 |
| 是否要支持多渠道筛选 | 当前只有 keyword/status | 首轮不加，保持最小闭环 |

## 11. 验收标准

如果后续实现，建议使用以下标准验收：

- 页面默认选中第一条客户记录，并清楚展示当前客户。
- 顶部客户切换条可以切换记录，客户状态、风险证据、时间线和行动区同步变化。
- 用户能从页面看出客户风险、负责人、状态、AI 建议和历史处理记录。
- 用户能点击主动作推进状态，操作后列表和时间线刷新。
- 用户能打开详情抽屉查看编号、客户、负责人、状态、AI 建议和闭环记录。
- 数据为空时页面不报错，有可理解的空状态。
- 不新增技术栈，不重构其他页面，不修改共用数据结构。
- 页面不采用固定三栏布局。

## 12. 推荐实施顺序

```text
第 1 步：顶部客户切换条可选择
第 2 步：主区域展示当前客户状态总览
第 3 步：补充风险与证据区
第 4 步：时间线只展示当前记录
第 5 步：底部行动区按状态展示主动作
第 6 步：补齐详情抽屉入口
第 7 步：运行最小验证
```

建议验证命令：

```bash
npm run build
```

如果只做局部页面调整，也可以先运行项目已有的类型检查或 lint 命令；以 `package.json` 中实际脚本为准。

## 13. 当前结论

客户 360 页面首轮不建议追求“大而全”的客户中台。最稳妥的方向是：

```text
把现有三栏占位页收敛成一个纵向客户处理闭环。
```

这样既能保持简洁，又能让页面从“展示信息”变成“推动处理”。后续如果有真实客户、合同、订单、触点接口，再逐步增强客户档案和互动聚合，不需要推翻首轮结构。
